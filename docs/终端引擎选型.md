# 终端引擎选型：godot-xterm 要不要魔改，要不要换 libvterm

结论先行：**不魔改，不替换，按原样用 godot-xterm。**

## 先更正一条

M0-c 的文档里，我根据 pyte 的表现列了「三条必须交给 godot-xterm 验证的序列」。
实测之后**三条都是 pyte 自己的缺陷，不是 godot-xterm 的问题**。

验证方法：`m0/probe/capture_stream.py` 录一份真实的 ttyS0 字节流
（含 vim、tmux 分屏、256 色、真彩、下划线），再喂给 libtsm ——
那正是 godot-xterm 实际使用的引擎（`lihop/libtsm`，godot-xterm v4.0.3 / 2026-02）。

| 序列 | pyte 0.8.2 | libtsm（godot-xterm） |
| --- | --- | --- |
| `CSI 6 n` DSR | 抛异常，需打补丁 | 正确回 `ESC[y;xR`；`CSI 5n` 回 `ESC[0n` |
| 设备属性查询 DA | 不应答 | 回 `ESC[>1;1;0c` / `ESC[?60;1;6;9;15c` |
| `CSI > 4;2 m` XTMODKEYS | 抛异常 | 源码里显式 `if (csi_flags & CSI_GT) { /* ignore */ }` |
| `ESC ( 0` DEC 特殊图形 | 不映射，tmux 框线显示成一整行 `q` | **正确渲染成 `────`（U+2500）** |

libtsm 另外确认具备：备用屏 `?1049`/`?47`、256 色、真彩、滚动区 DECSTBM、
插入删除行 IL/DL、OSC 标题。回写通道也接好了：`Terminal::_write_cb`
挂在 `tsm_vte_new` 上，发 `data_sent` 信号（`PackedByteArray`），
正好转发回 ttyS0。

## libtsm 确实缺的两样

`?2004` 括号粘贴、`?1006`/`?1002`/`?1003` SGR 与扩展鼠标上报（只有最老的 `?1000`）。

实测这两类**被静默忽略，不产生可见损坏**：喂进
`ESC[?2004h ESC[?1006h ESC[?1002h ESC[?1003h` 加 `ESC[200~...ESC[201~`
包裹符，屏幕干干净净，包裹符被当作 CSI 吃掉、不会变成乱码。

## 关键判断：缺口分两类，只有一类需要动引擎

- **渲染缺口** —— 必须改引擎才能修。**我们一条都没有。**
- **输入/应答缺口** —— 括号粘贴、鼠标上报都属于这一类，
  而我们的 C# 层本来就坐在 socket 和 Terminal 节点中间，
  两个方向的字节都经手。嗅探 `ESC[?2004h`/`l` 自己维护模式位、
  粘贴时自己加包裹符，大约十行，**不需要碰 godot-xterm 一行代码**。

另外：godot-xterm 的鼠标代码只有滚轮（滚屏）和选区，
**它根本不向客户机上报鼠标**。所以 `?1006` 这个缺口跟引擎无关，
换成 libvterm 一样要自己写上报逻辑。

## 为什么不换 libvterm

libvterm（neovim 维护的 fork，最近提交 2025-11）确实是更完整的状态机：
`?2004`/`?1006`/`?1002`/`?1003` 全有，还带 `mouse.c`、`keyboard.c`，
代码量与 libtsm 相当（5901 vs 5734 行）。

但它 `src/` 下**没有任何渲染层**，只是状态机。
godot-xterm 的价值是状态机 **加上** Godot 渲染、输入映射、主题字体、
以及三端预编译好的 GDExtension 二进制和 CI。

换引擎意味着：重写 `terminal.cpp`（1023 行）的绘制路径去对接 libvterm
完全不同的 screen API，然后永久维护一个 godot-xterm 的 fork，
还要自己为三端构建和分发 GDExtension。
换来的是两个我们能在 C# 层十行解决的特性。

概要书里「内部已含 ANSI 解析渲染；不需要 libvterm 中间层」这个判断成立。

## 复现

```bash
m0/run/venv/bin/python m0/probe/capture_stream.py   # 录真实字节流
# 然后用 m0/probe/tsmdump.c 喂给 libtsm 对照（编译方法见该文件头部注释）
```
